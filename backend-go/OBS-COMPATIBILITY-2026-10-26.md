# OBS 本地连接兼容修复（2026-10-26）

## 原因与修复

本机 OBS 日志显示连接 RTMP 后约三十秒报 `RTMP_Connect1, handshake failed`。对照上游源码与 Git 历史，内嵌 Go RTMP 自初始实现起只发送 S0/S1，未发送 S2；此前的测试发布器同样漏读 S2，因此没有发现此问题。

现在完整返回 S0/S1/S2，S2 回显 C1，收到 C2 后才处理业务命令。整个握手的读写都有十秒超时，写入不完整视为失败。测试发布器必须读取并验证 S2 后才能继续，补丁前该测试稳定超时，补丁后通过。协议依据：[RTMP 1.0 §5.2](https://rtmp.veriskope.com/pdf/rtmp_specification_1.0.pdf)。

上一轮资源修复将发布码改为 32 位，这是该轮新增行为。本次按需求恢复为八位，通过密码学随机数均匀选取字符；不含易混淆字符。活动房间、模式、唯一房间、发布者租约及撤销检查继续生效，观看票据与发布码仍独立。

配置下载原子补齐或迁移旧长度，十二个并发请求取得同一个落库八位码。已有八位码重复下载保持稳定；房主转交或关闭后，迟到的补码操作不能写入。32 位旧码需房主重新下载 OBS 配置后在 OBS 更新，转交后必须改用新房主的码。

## 验证

- Go 全套 `go test -count=1 ./...`、`go vet ./...` 和 Windows 后端构建通过。
- 真实 FFmpeg 推送合成 H.264/AAC，经房间观看票据访问后端 FLV，实际解码画面和声音；断开后再次发布与解码通过。
- 错误八位码被拒绝，原合法推流继续正常解码；未经观看授权的直接 FLV URL 返回 403。
- 真实 OBS 32.2.2 使用独立配置、合成画面和音频连接本地服务成功，持续超过一分钟，期间两次从后端鉴权 FLV 解码通过。测试不采集用户桌面、摄像头或麦克风。
- 本次不需要更改 Android/HarmonyOS 协议或重新构建安装包；没有操作 NAS 或发布 GitHub Release。外网 RTMP 穿透不属于本机验证结论。

本地测试数据、OBS 配置与日志均置于源码仓库外，不随 PR 提交。
